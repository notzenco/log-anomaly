# Design: host-based log anomaly detection

Status: written before implementation, revised after the first evaluation
run; implementation complete — results in [REPORT.md](../REPORT.md). Feature
names below match `log_anomaly.features.FEATURE_NAMES` as shipped.
Author: Zenco (github.com/notzenco).

---

## 1. Problem framing

**Goal.** Given a stream of host-level log records (authentication, privilege
elevation, process execution, outbound network connections), assign every
record an anomaly score such that a small number of ranked alerts surface
behaviour that a defender would want to look at.

**Why this is hard, and what "correct" means.** Anomaly detection has no
oracle. Two failure modes dominate:

1. *The base-rate problem.* Almost every record is normal. On an internet-facing
   SSH host, more than 99.9% of authentication records are failures from
   background scanners. An algorithm that flags everything achieves recall 1.0
   and is useless. Precision must therefore be reported next to the base rate,
   and alert volume per day is the unit an analyst actually lives with.
2. *The contamination problem.* The training period is never clean. If the
   training window already contains a brute-force campaign, an unsupervised
   model learns "lots of failures from that IP" as normal.

**What we optimise.** We are not building a classifier. We are building a
*ranking + explanation* system: a triage tool. The evaluation therefore
answers three questions in order:

- **Separation.** Do the scores of attack events separate from normal events
  (PR-AUC, ROC-AUC, per-attack-type recall)?
- **Volume.** At a chosen operating point, how many alerts does a defender
  receive per day?
- **Actionability.** Can a human tell *why* an event was flagged from the
  alert alone, without opening the raw log?

**Non-goals.** No live deployment, no streaming, no claims of generalisability
to networks or clouds we did not measure, no comparison against a production
SIEM.

## 2. Dataset choice

### 2.1 What we considered and rejected

| Candidate | Why not |
| --- | --- |
| LANL *Unified Host and Network* Data (auth + DNS + netflow) | Requires registration on lanl.gov, and the full release is ~700 GB. The auth component alone is ~2 GB gzipped. Not reproducible for a reader without an account. |
| LANL *Comprehensive Multi-Source Cyber-Security Events* | Same registration wall, plus multi-source joins that are out of scope for a first project. |
| CICIDS2017 / CICFlowMeter | Network flow datasets. The task is host-based; there is no process or authentication content to model. |
| HDFS, Thunderbird, BGL (Loghub) | Large (1.5 GB to 30 GB) and about distributed-system or supercomputer scheduling, not host security behaviour. |
| Windows CBS (Loghub) | 26 GB and mostly component-servicing noise. |

### 2.2 What we use

**Real data — the Loghub collection** (Zhu et al., ISSRE 2023; DOI
`10.5281/zenodo.8196385`). Freely downloadable without registration, permissively
licensed for research/academic use provided the repository is cited, and small
enough to fetch in CI-adjacent workflows. We use three members that between them
cover the three behaviour families:

| Dataset | Archive | Size | Content we use |
| --- | --- | --- | --- |
| **Linux** | `Linux.tar.gz` (md5 `6d1802d7778126f21c001c6aa7b6b106`) | 232 KB | `/var/log/messages` from a Linux server over 264 days. SSH/PAM authentication failures and success, `su` sessions, `ftpd`, and service logs. Single host `combo`. |
| **OpenSSH** | `SSH.tar.gz` (md5 `a44e40b4348697dabf2bba56885e0a38`) | 4.6 MB | OpenSSH server log over 28 days, 655k lines. Successful `Accepted password` logins alongside a large volume of internet background scanning. Single host `LabSZ`. |
| **Proxifier** | `Proxifier.tar.gz` (md5 `2612fce12cc3d16599ddb3db8e9c477a`) | 2.4 MB | Windows proxy log, 21k lines: application → `host:port`, bytes sent/received, connection lifetime. Used for network-behaviour features. |

`scripts/download_data.sh` fetches these from Zenodo, verifies the MD5 against
a pinned value, and refuses to use a file whose checksum does not match. Raw
data is git-ignored and never committed.

**Known limitation of the real data: no ground-truth labels.** Loghub marks
none of these three datasets as labelled. That means *no honest precision or
recall can be computed on them*. We therefore split the evaluation:

- **Real data** is used to validate the parser against genuine production log
  shapes, to show that the feature distributions are non-degenerate, and to
  report unsupervised quantities (alert volume per day, score distribution,
  and a manual audit of the top-ranked alerts with a stated rubric).
- **Synthetic data with labels** carries the quantitative evaluation. It is
  generated by `log-anomaly synth`, whose background traffic model is
  parameterised to resemble the real Loghub Linux/OpenSSH streams, and whose
  attack families are injected with known timestamps and labels.

Every table and chart in `REPORT.md` states which corpus it came from. The
synthetic corpus is labelled as synthetic wherever it appears — file header,
CSV column, CLI output, README, report captions.

### 2.3 Why the real data is still worth it

Three reasons that the synthetic corpus cannot cover:

1. **Parser realism.** Synthetic lines are written by us; real lines contain
   byte-level garbage, missing fields, odd program names and timestamps that
   jump across months. A parser that only survives on clean input is not
   useful.
2. **Realistic base rates.** The OpenSSH corpus has a true anomaly rate of
   roughly 0.03% *successful* authentications amid ~140k failures. Synthetic
   corpora usually have suspiciously round numbers; these do not.
3. **Rare, long-tail identities.** The real corpus contains users and source
   hosts that appear exactly once in 264 days. Whether the model is robust to
   that long tail is only testable on real data.

## 3. Feature engineering

The unit of analysis is the **event**, not the file. Each log line is parsed
into a normalised event, then enriched with time-windowed context. Features are
computed per event from a sliding window over the event stream, split into
three entity scopes:

- **user scope** — the account authenticating (e.g. `root`, `alice`).
- **host scope** — the machine the event occurred on.
- **source scope** — the remote peer address the event came from.

All count features are *trailing* windows (the window ending at the event),
which keeps the pipeline causal: scoring a log file offline reproduces exactly
what an online scorer would have produced at that timestamp.

### 3.1 Authentication features

| Feature | Scope / window | Signal |
| --- | --- | --- |
| `auth_fail_count_1h` | user, 1 h | failure burst against one account |
| `auth_fail_count_10m` | user, 10 m | tight brute-force burst |
| `src_fail_count_10m` | source, 10 m | one scanner hammering many accounts |
| `src_fail_count_1h` | source, 1 h | same, over the longer window |
| `src_distinct_users_1h` | source, 1 h | credential stuffing (many accounts, one source) |
| `src_user_entropy_1h` | source, 1 h | entropy of the user mix per source, high = spread out |
| `auth_fail_count_zscore` | user, causal running stats | failures relative to that user's own history |
| `login_count_1h` | user, 1 h | login burst (accept + session-open deduplicated per pid) |
| `user_distinct_hosts_1h` | user, 1 h | one account touching many machines |
| `new_user_host_pair` | user×host, lifetime | first time this account appears on this host |
| `new_src_for_user` | user×source, lifetime | first time this source is seen for this account |
| `unknown_user` | user, lifetime-to-date | account not seen earlier in the stream |
| `off_hours` | user, learned hour profile | login outside the account's learned working hours |
| `hour_profile_distance` | user, learned hour profile | circular distance from the account's modal hour |
| `root_activity` | — | activity attributed to `root` |
| `sudo_fail_count_1h` | user, 1 h | failed privilege escalation attempts |

### 3.2 Process features

| Feature | Scope / window | Signal |
| --- | --- | --- |
| `proc_pair_rarity` | (parent, child) pair, lifetime-to-date | −log count of the pair; large when rarely observed |
| `proc_pair_is_new` | (parent, child) pair | binary: pair not seen earlier in the stream |
| `proc_new_for_user` | (user, process) | this account has never run this program |
| `proc_freq_rarity` | (user, process) | −log of observed frequency for this account |

### 3.3 Network features

| Feature | Scope / window | Signal |
| --- | --- | --- |
| `net_conn_count_1h` | process, 1 h | connection burst from one application |
| `net_new_dest_for_proc` | (process, dest host) | first time this app talks to this host |
| `net_dest_rarity` | (process, dest) | rarity of the (application, destination) pair |
| `net_bytes_sent_zscore` | process, 1 h | bytes sent relative to that app's history |
| `net_total_bytes_1h` | process, 1 h | absolute volume in the window |

Six one-hot context features (`type_auth_failure`, `type_auth_success`,
`type_session`, `type_sudo`, `type_process`, `type_network`) complete the
31-feature matrix, so models can condition on event kind.

### 3.4 Design rules

- **No label leakage.** Features are computed from the event stream only. The
  synthetic labels live in a separate file and are never read during feature
  extraction.
- **Model fitting uses the training period only.** Scalers, PCA, the forest
  and the rarity distributions are fit on training rows. Feature *state*
  (seen pairs, running statistics, hour profiles) is deliberately causal
  rather than frozen at the training boundary: it may use any event *before*
  the one being scored, exactly as an online scorer would, so a pair is "new"
  only the first time it ever appears. No feature ever uses a future event.
- **Features are split, never shuffled.** A per-event matrix is built once for
  the whole corpus with strictly trailing windows, then cut by timestamp, so
  no test event can contribute to a training-window statistic.
- **Neutral fill.** If a feature cannot be computed for an event (e.g. no
  process events in a syslog-only corpus), it is filled with a documented
  neutral value rather than dropped, and its *availability* is tracked so the
  report can say which features were live for a given corpus.

## 4. Models

Three models, deliberately chosen to fail differently.

### 4.1 `rarity` — statistical baseline (no learning)

A transparent composite: every feature is converted to a surprise score
`−log P(X ≥ x)` under its empirical training distribution (floored so one
feature cannot dominate), and the composite is their sum. (As implemented;
the original draft used z-scores for count features, which behave badly on
the many zero-inflated features here, so the empirical tail is used
uniformly.) This is the "a good analyst would eyeball this" model, and it
exists so the ML models have to beat something interpretable rather than
beat nothing.

### 4.2 `iforest` — Isolation Forest

`sklearn.ensemble.IsolationForest`, default 100 trees, no hyper-parameter
search. Isolation forests assume anomalies are rare and different; they need
no density assumption and are cheap enough to rescore a whole corpus while
producing per-event explanations.

### 4.3 `pca-ae` — linear autoencoder (PCA reconstruction error)

Standardise, project onto the top `k` principal components fitted on training
data only, reconstruct, and score by squared reconstruction error. This is the
classical linear autoencoder: it has a fundamentally different inductive bias
from Isolation Forest (global covariance structure rather than local
isolation), and it gives *exact* per-feature attributions for free, because
the reconstruction error decomposes additively over features.

We deliberately avoid a deep autoencoder: `torch` would add hundreds of
megabytes of dependencies for a model that, on tabular features with a few
thousand rows, would not beat PCA by enough to matter. This is a deliberate
trade of a little headline appeal for a dependency-light, reproducible pipeline.

### 4.4 Explanations

Every model exposes a `contributions(X)` method returning a per-event,
per-feature contribution matrix:

- `pca-ae`: exact squared reconstruction error per feature.
- `iforest`: **occlusion** — for each feature, the feature is replaced by its
  training median and the score is recomputed; the drop in score is the
  contribution. Computed only for the top-k alerts, so it stays cheap.
- `rarity`: the feature's own rarity/z-score contribution.

## 5. Evaluation protocol

### 5.1 Splitting

Strictly **time-based**, never random:

```
|-------------- train (fit) -----------|--- validation (threshold) ---|------ test (report) ------|
```

- The corpus is cut at two timestamps chosen as fractions of the *duration*,
  not of the row count, so dense and quiet periods are treated fairly.
- All model fitting (scaler, PCA, Isolation Forest, reference statistics)
  happens on the training slice only.
- The operating threshold is chosen on the validation slice and then applied
  unchanged to the test slice. Thresholds are never tuned on test.

### 5.2 Metrics

- **Base rate**: fraction of positive events in the test slice, stated before
  any metric, next to every precision number.
- **PR-AUC** (average precision) as the headline, because it is base-rate
  aware; **ROC-AUC** reported for completeness with the caveat that it
  flatters rare-positive problems.
- **Precision / recall / F1** at the validation-selected threshold.
- **F5** as the security-oriented operating point: recall is weighted five
  times precision, matching an analyst who prefers to look at extra alerts
  rather than miss an intrusion. Both operating points are reported.
- **Alerts per day** at each operating point, and the number of distinct
  *entities* (users, hosts, sources) those alerts touch, which is closer to
  the real workload than raw alert count.
- **Per-attack-type** recall and precision, so a model that only catches
  brute force is not presented as a general detector.

### 5.3 Base rates, explicitly

The synthetic corpus is generated with realistic, *unequal* base rates per
attack family. We report the base rate of each family and the overall base
rate, and we show how precision changes as the threshold moves, so the reader
can see the operating curve rather than a single flattering point.

### 5.4 Real-data evaluation

No labels means no precision/recall. On the real corpora we report:

- alert volume per day at fixed score quantiles and at a fixed operational
  budget (e.g. 20 alerts/day),
- the score distribution,
- and a **manual audit**: the top 100 alerts are read and classified by hand
  against a written rubric (malicious / benign-but-unusual / noise), with a
  Wilson confidence interval on the resulting precision estimate. The rubric
  and the audit labels are committed so the number is checkable.

## 6. Limitations

Stated up front, because a security project that hides these is a marketing
exercise.

1. **The labelled evaluation is on synthetic data.** Its numbers are a
   property of the generator and of the injection assumptions, not of the
   real world. Treat them as a regression test on the *pipeline*, not as
   evidence of detection capability.
2. **No labels on the real data.** Precision on the real corpora is a manual
   audit estimate with a wide interval, not a measured quantity.
3. **Single-host corpora.** Loghub Linux and OpenSSH are one host each, so
   per-host features are nearly degenerate there. The design supports
   multi-host, but it has not been demonstrated at scale.
4. **Log-based visibility only.** The attacker sees everything the log shows.
   A compromise that avoids logging, or that keeps to a normal-looking
   process tree, is invisible to this system by construction.
5. **Contamination.** Training windows in the real corpora certainly contain
   attacks; we do not know which events are attacks, so we cannot measure how
   much that hurts.
6. **Timestamps without a year.** The Loghub syslog lines carry month, day and
   time only. We infer a year and handle the December→January rollover
   explicitly; the inferred year is recorded in the artefact metadata.
7. **Single-threshold triage, not response.** The system ranks and explains.
   It does not block, isolate or ticket.
8. **Feature set is hand-designed.** No feature selection, no interaction
   search, no hyper-parameter tuning. That keeps the result interpretable and
   the runtime small, but it leaves performance on the table.
